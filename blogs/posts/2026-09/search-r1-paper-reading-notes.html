Search-R1《Training LLMs to Reason and Leverage Search Engines with Reinforcement Learning》阅读笔记

论文阅读机器学习智能体强化学习
2026 年 9 月 14 日约 8 分钟阅读

这篇笔记阅读 Jin 等人的 Search-R1: Training LLMs to Reason and Leverage Search Engines with Reinforcement Learning。它要解决的问题很具体：模型不仅要会推理，还要自己决定何时搜索、搜什么、读完结果后是否继续搜索；这些决策能不能只靠最终答案对错，用强化学习练出来？

贡献：把搜索放进强化学习的完整过程

普通 RAG 通常先按原问题检索，再把结果交给模型回答。ReAct、IRCoT 可以多轮检索，但主要依赖提示词教模型如何行动。Search-R1 把模型生成的推理、搜索请求、检索器返回的文本、后续推理和最终答案放进同一条训练轨迹，直接对整段交互做强化学习。模型不需要人工标注“这一步应搜哪个词”的示范轨迹；训练信号主要是最后答案是否正确。

它沿用 PPO 或 GRPO 做策略优化，最重要的工程改动是检索结果的 token 不参与策略损失。这样模型学习的是自己能控制的部分——推理、查询词和答案，而不是被当成“生成了”搜索引擎返回的段落。

背景：为什么给普通 R1 接一个搜索框还不够

假设问题要先查一位作者的出生地，再查这个地点所属的国家。一次性检索原问题可能找不到两个环节的证据。更合适的过程是“先想缺什么 → 搜索 → 读结果 → 更新问题 → 再搜索”。只在推理时让模型调用搜索工具，并不能保证它学会何时搜索、如何改写查询；而收集大量标准搜索轨迹做 SFT 又很费人工。Search-R1 选择让模型在训练时自己试错：搜得好、推理得对，最终答案更可能正确，整条由模型产生的行动就得到更好的强化信号。

方法：一条训练轨迹怎样产生

  1. 给问题和格式说明：模型在 <think> 中推理；需要外部信息时，在 <search> 与 </search> 之间写查询；确定答案后，在 <answer> 中作答。模板只规定交互格式，没有给每一步的标准搜索词。
  2. 边生成边检索：训练系统看到搜索标记就暂停生成，取出查询词调用检索器，再把返回的段落放入 <information> 区块，接在上下文后让模型继续。模型可以继续搜索，也可以结束；训练设置有最大行动预算。
  3. 只看最终答案给奖励：从 <answer> 中提取预测答案，与标准答案做精确匹配（EM）。对了给正向信号，错了则没有；论文不另训神经奖励模型，也不为每次搜索设置单独的“好查询”奖励或格式奖励。
  4. 更新模型，再采样：用 PPO 或 GRPO 比较采样轨迹的好坏，更新模型自己生成的 token；继续让更新后的模型与检索器交互。搜索动作不可微，但策略梯度仍能把最终奖励传回更早的查询词选择。
示意，不是论文原样本：问题“某位导演出生在哪个国家？”→ <think>先查出生城市</think> → <search>导演姓名 birthplace</search> → <information>检索结果写着某城市</information> → <think>还要确定城市所在国家</think> → 再搜索 → <answer>国家名</answer>。训练时评判的是最终答案，不要求中间查询词与某条人工标准轨迹完全一样。

关键细节：为什么要屏蔽检索文本的 loss

一条轨迹在页面上看起来是一整段文本，但其中有两种来源：模型写的 <think>、<search>、<answer> 内容，和检索器送来的 <information> 内容。后者应作为模型继续推理时能读到的上下文，却不是它自己选择生成的行动。如果照普通语言模型那样给每个 token 都计算 PPO／GRPO 损失，模型会被要求“对检索器写出的词负责”，更新目标就混淆了。

Search-R1 给 token 一个开关：模型生成的 token 记为 1，检索来的 token 记为 0；策略损失和与参考模型的 KL 项只在前者上计算。屏蔽损失不等于把搜索结果从上下文删除。模型仍能读结果并据此决定下一步，只是不因工具返回了哪些字而直接受奖惩。这个区分是将普通 R1 式强化学习用于工具交互时的核心实现点。

PPO 与 GRPO 在这里是两种可替换的优化器：PPO 训练一个价值模型估计行动好坏；GRPO 对同一个问题采样多条答案，用组内成绩作相对基线，不另训价值模型。论文主实验默认使用 PPO，并专门比较 GRPO；不能把 Search-R1 理解为“只用了 GRPO”。

实验：收益来自哪里，范围有多大

论文把 NQ 和 HotpotQA 的训练问题合并，用它们训练 Qwen2.5-3B／7B 的 Base 与 Instruct 模型；测试覆盖 NQ、TriviaQA、PopQA、HotpotQA、2WikiMultiHopQA、Musique、Bamboogle 共七个问答集，指标是最终答案的 EM。对比检索方法共用2018 年 Wikipedia 快照、E5 检索器和每次返回 3 段文本。这里的“实时”指每条轨迹在运行中即时检索，不代表联网查最新网页。

对 7B 来说，43.1 相比最强的这两项基线 34.8，高 8.3 个百分点，相对提高约 24%；3B 的 32.5 相比 RAG 27.0，高 5.5 个百分点，相对提高约 20%。这些是七个数据集的平均值，不是每个单独数据集都胜出；例如 3B 的 Bamboogle 上，Search-R1-Instruct 为 26.4，低于论文中的 Search-o1 提示基线 32.0。

消融结果尤其能说明方法。用 Qwen2.5-7B-Base 与 PPO 时，屏蔽检索 token 的七集平均 EM 为 43.1，不屏蔽只有 34.3。比较优化器时，GRPO 通常收敛更快，但论文观察到训练过久会出现奖励坍塌；PPO 起步较慢、整体更稳定。它并非声称 PPO 在每个模型上最终分数都最高，例如 3B-Instruct 的 GRPO 平均 33.6，高于 PPO 的 32.5。

如何理解它与前面几篇论文的关系

IRCoT、ReAct 主要在推理时用提示组织多轮检索；FireAct 用成功的搜索轨迹做监督微调；Search-R1 则让模型在训练中实际搜索，用最终答题奖励更新查询和推理策略。这三者都可呈现“思考—搜索—再思考”，但学习信号不同。Search-R1 的收益说明搜索决策可以不依赖逐步示范来训练；也说明把外部观察与模型行动分清，是让强化学习目标正确落地的前提。

边界同样明确：主实验是固定 Wikipedia 语料上的问答，不是开放网页搜索；奖励只检查答案是否与标准答案精确一致，不能保证引用可靠、查询高效或对开放式任务有用。没有逐步奖励也意味着模型究竟为何得到正确答案仍需单独分析。因此，这篇论文更像“如何把可验证问答中的搜索调用接入 RL”的扎实起点，而不是通用搜索智能体已经解决的证明。
