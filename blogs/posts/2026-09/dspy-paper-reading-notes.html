DSPy《Compiling Declarative Language Model Calls into Self-Improving Pipelines》阅读笔记

论文阅读机器学习提示优化语言模型流水线
2026 年 9 月 14 日约 8 分钟阅读

这篇笔记阅读 Khattab 等人的 DSPy: Compiling Declarative Language Model Calls into Self-Improving Pipelines。它讨论的不是怎样写出一条更漂亮的提示词，而是一个更上层的问题：当应用要连续调用语言模型、检索器和工具时，能不能先写清每一步要做什么，再让系统根据数据自动寻找合适的示例和提示方式？DSPy 给出的答案是把调用写成可组合的程序模块，再“编译”这个程序。

贡献：把手调 prompt 变成优化流水线

论文的核心贡献有两部分。第一，提出 signature（签名）和 module（模块），把“问答”“生成检索词”“先推理再回答”等语言模型操作写成清晰、可复用的组件。第二，提出由 teleprompter（优化器）驱动的编译流程：运行整个程序，收集成功轨迹中的中间步骤，再为每个模块自动挑选示例，尽量提高最终任务指标。开发者仍决定任务拆成几步、怎样连接工具以及什么算正确；不必逐句手写每个模块的长 prompt。

这里的“编译”不是把 Python 变成机器码。它指的是：给定程序、少量任务样本和评价指标，搜索或生成更合适的模块参数。最常见的是优化提示中放哪些 few-shot 示例；论文也展示了微调模型权重，以及通过集成多个程序调整外层流程的方式。

背景：多步应用为什么比单条 prompt 更难调

设想一个两跳问答系统：模型先根据问题生成检索词，检索器找资料；模型阅读资料后再生成第二个检索词，最后根据两轮资料回答。若第一步的 prompt 让模型写出太宽泛的词，后面的回答模块即使提示写得很好，也拿不到关键证据。反过来，只调检索模块而不检查最终答案，也不知道改动是否真的有用。多步流水线的问题是各步骤互相影响，不能只凭某一步的输出看起来顺眼来调系统。

传统做法会为每一步写固定的任务说明、角色设定和示例；换模型、换数据领域或调整流水线后，又得重新手调。DSPy 希望保留程序结构由人设计的灵活性，同时让模块内部的提示示例可以依据最终任务的评价指标自动调整。

方法：从声明任务到编译程序

第一层是 signature：说明输入和输出。例如 question -> answer 表示输入问题、输出答案；context, question -> search_query 表示读已有资料和原问题，再给出下一轮检索词。它只写“要完成什么转换”，不在此处指定一整段任务专属 prompt。字段名称和可选说明会帮助 DSPy 构造实际调用。

第二层是 module：决定怎样完成转换。Predict 直接预测输出，ChainOfThought 先生成推理再给答案，Retrieve 调检索器。开发者可以把这些模块放入普通 Python 控制流中，例如“生成检索词 → 检索 → 再生成检索词 → 再检索 → 回答”。这一步固定的是应用的总体结构，不是某个模型所需的具体示例文本。

第三层是 teleprompter：优化每个模块。编译器读取程序、训练样本和评价指标，逐层找到需要模型预测的模块。以论文的 BootstrapFewShot 为例，它先让未优化的程序（或指定的 teacher 程序）跑若干训练问题；如果最终答案通过指标，就保留该次运行里“生成了什么检索词、看到了什么上下文、最后如何回答”的完整轨迹。这样即使数据只标注了最终答案，也能从成功轨迹中为中间模块构造示例。示例组合再根据验证数据或训练集内交叉验证来选择，而不是直接在测试集上挑。

  1. 人先写程序：确定模块、模块间的数据流、训练问题，以及可计算的目标指标，例如最终答案是否与标准答案一致。
  2. 编译器试跑并收集：让程序完成这些问题；丢弃不符合指标的轨迹，把成功轨迹中各模块的输入—输出对变成候选 few-shot 示例。
  3. 选择或学习参数：在候选示例之间搜索，或把收集到的数据用于微调较小模型；得到编译后的各模块。
  4. 实际使用：对于通常的 few-shot 编译，新问题仍按原来的检索、推理、回答顺序运行，只是每个模块携带了编译得到的提示示例；微调型编译则会调用更新过权重的模型。

一个具体例子：训练样本只有“问题：某作者出生的城市在哪个国家？”和最终正确国家，没有人工写的两轮检索词。若 DSPy 某次试跑恰好先搜到作者出生城市、再搜到该城市所属国家，并答对了，它就能把两次生成检索词的过程留下来，作为以后生成检索词的示范。这里的“自我改进”发生在编译阶段，靠成功轨迹与指标筛选；默认不是上线后每回答一题就自动在线学习。这个例子是对算法的示意，不是论文中的原始测试题。

实验：结构和编译分别带来什么

作者主要研究两类任务。GSM8K 数学题：使用 200 道训练题、300 道开发题，并在官方测试集上报告部分设置。GPT-3.5 的 ChainOfThought 程序如果使用人工写好的推理示例，测试准确率为 72.4%；用 DSPy 自举示例而不依赖这些人工推理链，达到 72.9%。更复杂的“生成多条推理再比较”程序，经自举后为 76.0%。这说明收益不只是换了一个提示模板：模块设计和示例优化都在起作用。不同程序的数字不能单独当作“编译器的净增益”。

怎样理解这篇论文的边界

DSPy 把原先难以复用的 prompt 调整，变成可以围绕数据和指标重复运行的优化过程；对多步检索、推理、工具调用尤其有吸引力。但它并不会自动发明一个好任务定义：程序结构和指标仍由人提供。如果指标只检查答案字面相同，可能选出“碰巧答对但证据不可靠”的轨迹；如果缺少可用反馈，编译器也难以判断哪些中间示例值得保留。此外，编译期要反复试跑程序，有额外模型调用成本。论文结果证明了特定任务和设置下的收益，不能保证任何新流水线都会自动变好。

我认为最值得带走的区别是：ReAct、CoT、RAG 主要回答“系统按什么步骤工作”；DSPy 进一步回答“这些步骤里的模型调用怎样根据任务数据被系统性优化”。在默认的 few-shot 编译中，变的是模块提示里的示例；只有选择微调型优化器时，语言模型的参数才会改变。
